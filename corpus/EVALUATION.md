## 怎么读这份数字（诚实声明）

1. **57.1% 才是当前 taint 引擎的真实 Precision**（把 3 例已登记边界算回误报）。
   之前的 100% 只测了 builtin，taint 规则从未被计分——接入后立刻暴露 3 个误报。
2. 3 个误报中 2 个已带反证（「字面量目标主机」「文件名剥离」），复核人可在数秒
   内结案；这是「报告但附推翻线索」的设计，不是缺陷，但也如实计入误报。
3. SQL-003（switch 白名单）是唯一没有任何反证线索的误报，需要跨语句常量收敛
   分析才能解决，属 Stage C-3 能力，已登记在 known-limitations.json。
4. 这是 train 划分的人工样本，任何口径的数字都只证明「流水线可用 + 引擎行为
   符合设计」，不构成真实准确率声明。
5. 评测器经过负向测试：篡改标准答案能正确产生 FP / FN；登记条目不再复现时
   会被标记过期（防止 known-limitations.json 腐烂成免检白名单）。

## 本轮修复的真实引擎缺陷（语料驱动）

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | 字符串字面量里的标识符被当变量引用（`"?nonce="` 中的 nonce） | 传播与终点匹配前剥离字符串与注释 |
| 2 | URL 主机为字面量时仍无任何反证提示 | 新增「字面量目标主机」反证（不断言安全） |
| 3 | `FilenameUtils.getName` 等文件名净化不被识别 | 净化模型新增「文件名剥离」信号 |
| 4 | 同行多污点变量取第一个而非真正传入调用的 | 改取行内最后出现的变量 |

## 已登记能力边界（见 known-limitations.json，每次评测公示）

1. **SQL-003 / JAL-SQL-101**：switch 表达式白名单收敛，逐行引擎无法理解 → Stage C-3
2. **PATH-003 / JAL-PATH-101**：净化信号按设计只作反证不断言安全 → 保持现状
3. **SSRF-002 / JAL-SSRF-101**：字面量主机 + 编码参数，仍需防 @ 与路径注入 → 保持现状

## 复现

    python corpus/tools/validate_corpus.py
    python corpus/tools/evaluate_corpus.py --strict-locations

校验器会对整个 `corpus/` 执行匿名化卫生检查，命中时只输出文件、行号和类型，绝不回显匹配内容。

## 扩产路线（按语料库规划）

1. 每类扩到 5 危险 + 5 安全/边界 → 约 150 案例，覆盖 15 个漏洞类别
2. 跨方法样本（Controller → Service → Mapper）≥ 30 个
3. 权限矩阵样本 ≥ 20 个（authz 覆盖率作为被测指标）
4. 真实项目脱敏样本（从已验证的真实 Spring Boot 项目提取最小调用链）
5. train / validation / holdout 三分（60% / 20% / 20%），holdout 只在发布前运行
